# 00. ワークショップ設計

対象：エンジニアだが AI を使った開発の経験は浅い（プロンプトの書き方くらいは知っている）後輩 7〜15 名。
形式：オンライン・1日（10:00〜17:00、昼休み1時間）。

---

## 1. このワークショップのゴール

**成果物**：Otoko Board に機能をひとつ追加した Pull Request を、1人1本出す。

**持ち帰ってほしい理解**：

> AI 開発の質を決めるのは、プロンプトの言い回しではなく
> **文脈（Context）・検証（Verification）・粒度（Scope）** の3つである。

参加者は「プロンプトエンジニアリング」だけを知っている状態で来ます。
この日の一番の価値は、そこから次の3つに視点を移すことです。

| 柱       | 何を教えるか                                                                                                         | この日どこで体験するか |
| -------- | -------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| **文脈** | AI の出来は「何を読ませたか」で決まる。うまい言い回しより、`CLAUDE.md`・対象ファイルの指定・受け入れ条件のほうが効く | Level 1・Level 5       |
| **検証** | AI に「自分で正しさを確かめる手段」を渡す。テスト・型・ビルドが通るまで回させる                                      | Level 2・Level 3       |
| **粒度** | 大きく頼むほど失敗する。1タスク＝1セッション＝小さな差分に切る                                                       | Level 3・Level 4       |

---

## 2. 段階設計：AI に任せる範囲を5段階で広げる

「段階的に教える」を、**AI への委譲範囲を1段ずつ広げる**という形で設計しています。
各 Level は前の Level を土台にしていて、飛ばすと後で崩れます。

| Level | テーマ       | 参加者がやること                                           | プロンプトの自由度         | 所要 |
| ----- | ------------ | ---------------------------------------------------------- | -------------------------- | ---- |
| **1** | **聞く**     | コードを1行も変えずに、AI にリポジトリを説明させる         | 完全にコピペ（`/explain`） | 30分 |
| **2** | **直す**     | 再現手順つきのバグを、テストを先に書かせてから直させる     | 完全にコピペ（`/fix-bug`） | 35分 |
| **3** | **作る**     | Plan mode で計画を出させ、承認してから実装させる           | テンプレの穴埋め           | 60分 |
| **4** | **任せる**   | Issue を自分で選び、受け入れ条件を自分で書いて任せる       | 自分で書く                 | 55分 |
| **5** | **仕組み化** | `CLAUDE.md` とスラッシュコマンドを自分で書き、環境を育てる | 自分で書く                 | 30分 |

Level 1〜2 では **プロンプトを一切考えさせません**。これは手抜きではなく、
「同じ入力なのに出力が違う」「同じ入力でも文脈次第で結果が変わる」を
全員が同じ土俵で観察するための設計です（→ 懸念1への打ち手）。

Level 3 でテンプレの穴埋め、Level 4 で初めて自分で書く、という順で自由度を上げます。

## 3. 想定される事故と、その打ち手

### 懸念1：プロンプトを考えさせると成果物に差が出て、進行が崩れる

| 打ち手                      | 内容                                                                                                                                                                                             |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **プロンプトを配る**        | Level 1〜3 はスラッシュコマンド（`/explain` `/fix-bug` `/plan-feature` `/verify`）としてリポジトリに同梱済み。参加者は `/explain` と打つだけ                                                     |
| **仕様を Issue で固定する** | 課題は事前に Issue 化し、**受け入れ条件を運営が書いておく**（[docs/05-issues.md](05-issues.md)）。「何を作るか」で迷う時間をゼロにする                                                           |
| **合流ブランチを用意する**  | 各 Level の完成形を `step/1-done` 〜 `step/4-done` として事前に用意。詰まった人は `git switch -c 自分の名前-work step/3-done` で**最新地点から再合流できる**。これが進行差を吸収する最大の仕掛け |
| **タイムボックス厳守**      | 終了時刻が来たら、完成していなくても合流ブランチに切り替えて次へ進む。「終わらなかった」を事故ではなく**設計どおり**にする                                                                       |
| **Level 4 だけ自由にする**  | 差が出てよいのは Level 4 のみ。ここは Issue を難易度別（★☆☆〜★★★）に用意し、選択そのものを学習にする                                                                                             |

### 懸念2：AI の作業時間が長くて暇な人が出る

| 打ち手                               | 内容                                                                                                                                                 |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **タスクを1回2〜4分に切る**          | 課題の粒度を「1ファイル＋1テスト」程度に設計。5分以上かかる依頼は分割する、と参加者に明示する                                                        |
| **Plan mode を必須にする**           | Level 3 以降は「計画を出す→人間が読んで承認→実装」。**待ち時間が『計画を読む時間』に変わる**ので手持ち無沙汰が消える                                 |
| **観察カードを埋めさせる**           | AI が動いている間に3項目だけ書く（[docs/07-worksheet.md](07-worksheet.md)）。「AI が何を読んだか」を必ず1つ書き写させる。これが Level 5 の材料になる |
| **早く終わった人はレビュアーになる** | 完了した人から他人の PR をレビューする係に回る。待ち時間対策と学習を同時に解決する                                                                   |
| **ストレッチ課題を常備**             | ★★★ の Issue を人数分より多く用意し、「早く終わったら次を取る」を最初に宣言しておく                                                                  |
| **`/clear` を習慣づける**            | Level が変わるたびに `/clear`。会話が長いほど1ターンが遅く・重くなることを体感させる                                                                 |

> 参加者への言い方：**「AI が動いている間は見ているだけの時間ではなく、読む時間です」**。
> ツール呼び出し（Read / Edit / Bash）が流れるのを追うだけで、AI が何を文脈にしたかが分かります。

### 懸念3：Claude Code の初期コスト（各自に課金してもらう必要がある）

**推奨：会社の Anthropic Console で API キーを発行し、参加者ごとに予算上限つきワークスペースを割り当てる。**

個人課金は避けます。理由は3つ：

1. 事前課金は**脱落ポイント**になる（当日「まだ払ってません」が必ず出る）
2. 経費精算の手間が人数分かかる
3. 運営が**誰がどれだけ使っているかを把握できない**（当日の進行判断ができない）

API キー方式なら、Console 上で1人ずつの使用量がリアルタイムに見えます。
「あの人だけトークンを使いすぎている＝たぶん詰まっている」が分かるので、**メンター投入の判断材料**にもなります。

詳細な比較・見積もり・配布手順は [docs/06-cost.md](06-cost.md) を参照。

### 懸念4：5時間の利用上限に引っかかる

**根本対策：API 従量課金には Pro / Max のような「5時間ローリングウィンドウ」の制限がありません。**
懸念3を API キー方式で解決すると、この懸念も同時に消えます。これが API キー方式を推す最大の理由です。

個人 Pro / Max プランで開催する場合の対策は次のとおり（[docs/06-cost.md](06-cost.md) に詳細）：

| 打ち手                           | 内容                                                                                                                                                          |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **モデルを Sonnet に固定**       | `.claude/settings.json` に `"model": "sonnet"` を設定済み。参加者が触らなくても全員 Sonnet で始まる                                                           |
| **初回打鍵の時刻を全員そろえる** | 5時間ウィンドウは「最初のメッセージ」から始まる。**10:45 に全員一斉にスタート**すれば、15:45 に全員一斉にリセットされる。運営がリセット時刻を読めるようになる |
| **重い作業を新ウィンドウに置く** | 15:45 のリセット後に Level 5 と PR 作成を配置（タイムテーブル参照）                                                                                           |
| **昼休みをウィンドウに食わせる** | 10:45 開始なら 12:00〜13:00 の1時間はウィンドウ内だが消費ゼロ。実質の作業は4時間に収まる                                                                      |
| **`/clear` を徹底**              | 長い会話は毎ターン履歴を再送するため消費が増える。Level ごとに `/clear`                                                                                       |
| **逃げ道を3つ用意**              | ①合流ブランチで先へ進む ②ペアの環境で続きをやる ③運営が予備 API キーを配る                                                                                    |

## 4. リポジトリを事前に用意する意味

参加者が自前でプロジェクトを作ると、当日の1〜2時間が環境構築で溶けます。
このリポジトリを配ることで、**当日の最初の打鍵から本題に入れます**。

同梱済みのハーネス：

- 動く状態のアプリ（React + TypeScript + Vite）とグリーンなテスト
- `npm run verify`（format + typecheck + test + build）── **AI に渡す「検証ループ」の実体**
- `.claude/settings.json` ── モデル固定と、よく使うコマンドの許可設定（許可ダイアログで止まらない）
- `.claude/commands/` ── 配布用プロンプト5本（`/explain` `/fix-bug` `/plan-feature` `/verify` `/self-review`）
- `CLAUDE.md` ── 最小限だけ書いてある。**Level 5 で参加者が自分で育てる余白**として意図的に薄くしてある
- `npm run doctor` ── 事前準備の完了判定（この出力のスクショを提出させる）
- GitHub Actions CI ── PR に赤/緑が出る。「人間が見なくても検証される」体験
- Issue / PR テンプレート ── 受け入れ条件を書く型を強制する

## 5. この設計であえてやらないこと

- **ゼロからのアプリ開発**：達成感は大きいが、テーマ決めと環境構築で進行が崩壊する
- **複数エージェントの並列実行**：初心者には制御できず、待ち時間問題も解決しない
- **MCP サーバーの導入**：設定が重く、当日のトラブル源になる。Level 5 の「次に学ぶこと」として紹介だけする
- **プロンプトのコツ集の暗記**：この日の主題ではない。文脈・検証・粒度の話に時間を使う
